# Product and Technical Specification: Native ASCII Music Broadcast Studio

Phase 2 • GPT-6 Sol • 24 September 2026 • Planning artifact, not an implemented app

This document turns the [Phase 1 visual system specification](PHASE_1_ASCII_ANSI_VISUALIZATION_SPECIFICATION.md) into a buildable iOS, iPadOS, and macOS product. It preserves Phase 1's playlist Visual DNA, visual score, persistent entities, four temporal scales, text-native rendering, confidence-aware music response, protected titles, deterministic checkpoints, and output safety envelope. The initial release broadcasts eligible **user-controlled local audio files** to a configured YouTube Live RTMPS ingest endpoint. The creator must have the rights required to transmit each recording, composition, artwork, and other included material. File possession and an in-app declaration do not establish those rights.

Numbers below are design targets until hardware, network, accessibility, and ingest prototypes measure them. All provider constraints must be rechecked before release. Phase 3 implementation is assigned to **GPT-6 Luna**; escalation can be used for difficult AVFoundation, concurrency, Metal, encoding, and transport problems. No application implementation begins in Phase 2.

## 1. Product definition and release boundary

The product is a native creative instrument that turns an ordered music program into a coherent, changing visual broadcast. The default path is: **choose eligible files → arrange a playlist → Generate Visual Identity → preview → check rights and output → go live → monitor and recover**. A playlist is an editable program, not merely a queue. A generated identity is an editable asset; changing a playlist does not erase the user's art direction.

The viewer receives encoded music, animated glyph artwork, and readable now-playing information. The creator receives a responsive local preview, clear broadcast state, an immediately usable automatic direction, and optional guided or advanced controls. First use should reach a convincing offline preview without requiring an account or stream key. A bundled or locally generated demonstration may be previewed and exported.

**Initial controlled release:** local files on macOS, iPadOS, and iOS; a single playlist and one YouTube RTMPS destination; 720p/1080p profiles after device qualification; offline preview; optional local proof recording; automatic plus guided controls; session restoration. Advanced authoring can follow after the core visual proof, but its storage contracts are designed now. macOS is the recommended host for unattended multi-hour channels. iPhone and iPad support foreground broadcasting on qualified hardware, with explicit interruption and screen-lock limitations. No promise of indefinite mobile background broadcast is made. Apple's background execution facilities are for particular supported activities, and a continued processing task is described as completing long-running work, not guaranteeing an endless channel. [Apple background execution](https://developer.apple.com/documentation/Xcode/configuring-background-execution-modes), [continued processing tasks](https://developer.apple.com/documentation/BackgroundTasks/performing-long-running-tasks-on-ios-and-ipados).

**Deferred:** YouTube account management API, multi-destination output, remote control, cloud rendering, scheduling while the app is closed, automatic royalty clearance, and semantic ML labels until validated. These are explicit future work, not incomplete claims about the release.

## 2. Source capability and rights model

Each source exposes separate, typed capabilities: catalog/playlist metadata; controllable playback; accessible decoded PCM; and permission to analyze. Rights status is an explicit creator attestation with evidence notes and expiry/review fields where applicable; the app cannot certify legal sufficiency. The broadcast gate requires an eligible technical path and a completed rights declaration for every included asset. Unknown/denied status excludes that item from a live queue and explains why.

| Source | Playlist metadata | Playback | Raw PCM in our pipeline | Analysis | Broadcast eligibility in initial release |
|---|---|---|---|---|---|
| User-selected local or Files/iCloud Drive file | Yes after import | Yes if format decodes | Yes if unprotected and decodable | Yes for permitted local file | Conditional on user's necessary rights and platform/source restrictions; default rights status unknown |
|  |
| Locally stored track surfaced by Apple media library | Metadata may be available | Depends on asset and access path | Only if a separate, user-accessible, unprotected file is selected and verified | Only for that independent file path | Treat as the local-file row only after independent file/rights verification; a library entry alone is insufficient |
|  |

If a creator independently imports a local file with a similar song name, the file is evaluated on its own. Album artwork is shown on the encoded output only when its use is covered; missing rights yield typography and generated art instead. YouTube scans live streams and may interrupt licensed third-party music unless a rights holder allowlists the channel through Content ID; preflight explains this without implying that allowlisting replaces licensing. [YouTube live copyright guidance](https://support.google.com/youtube/answer/3367684).

## 3. Product behavior and UX architecture

### First run and daily loop

Onboarding has five short steps: choose local music, assemble/choose playlist, generate identity, preview, configure output. “Go Live” is available only after a deliberate preflight. Users whose YouTube live access is pending remain productive in preview or local recording; YouTube says first-time enablement may take up to 24 hours. [YouTube encoder setup](https://support.google.com/youtube/answer/2907883).

The playlist editor supports multi-file import, drag/drop where available, multi-select, reorder, remove, search, sort, filter, duplicate detection, metadata inspection/editable local overrides, track audition, unavailable-item repair, and playlist save/duplicate. Sorting changes the view until the user explicitly applies a new play order. Removing from a playlist never deletes a source file. An imported file is referenced by durable access/bookmark or an explicitly chosen managed copy policy; security-scoped access is acquired and released correctly. A stale bookmark triggers “Locate file,” preserving the playlist entry and prior analysis. [Apple file importer](https://developer.apple.com/documentation/swiftui/view/fileimporter%28ispresented%3Aallowedcontenttypes%3Aoncompletion%3A%29), [Apple bookmark guidance](https://developer.apple.com/documentation/Foundation/NSURL).

“Generate Visual Identity” starts a cancellable analysis job and shows phases, coverage, partial results, and an early preview. The program can be previewed with incomplete analysis using Phase 1's confidence fallback; the UI labels that preview “still analyzing” and updates future passages when ready. The completed output includes a one-line identity rationale, editable DNA controls, a score timeline, and first/final title treatments. Regenerating creates a new variant; existing variants, user locks, and undo history remain available.

The preview workspace exposes **Preview, Playlist, Now Playing, Scene, Visual DNA, Effects, Output, Stream Health** as information groups, progressively disclosed. One program image is authoritative; the UI preview subscribes to it at its own refresh rate. While live, editing occurs in a reversible draft preview. “Take Live” atomically commits a compatible visual revision at a safe cue boundary or immediately for harmless changes; “Revert” discards the draft. A clearly labeled direct-edit mode is an expert choice. Reset parameter/section, undo/redo, favorite/duplicate, compare presets, import/export, and last-known-good defaults make experimentation safe.

Automatic mode does all scoring without manual mappings. Guided controls are Theme, Intensity, Complexity, Color, Glyph vocabulary, Motion, Glitch, Typography, and Camera. Each has a meaningful before/after preview and a safe range. Advanced controls expose family weights, scene exclusions/dwell, feature-to-action mapping, attack/release envelopes, motif and palette locks, title treatment, effect cooldowns, transition rules, seeds, overlays/branding and per-track overrides. Unsupported controls are disabled with reasons. Presets are schema-versioned manifests plus references to installed authored resources. Import validates resource IDs, caps, font licenses and safety eligibility; export strips file paths, stream keys and rights declarations. Unknown future fields survive roundtrip where safe, but cannot execute arbitrary code.

### Broadcast state and failure language

Separate **transport state** from **YouTube viewer-live status**. With a manually entered RTMPS URL/key, the app can verify local encoder readiness, network connection, ingest acknowledgement/bytes sent, and perhaps read-only provider health if later integrated. A connected socket alone does not prove the YouTube event is visible to viewers. Label this accurately: “Sending to YouTube; confirm in Live Control Room” until provider confirmation or user confirmation is available. [YouTube broadcast/stream lifecycle](https://developers.google.com/youtube/v3/live/guides/implementation/broadcasts-and-streams).

Model two orthogonal values. `LocalPipelineState = offline | previewing | preflighting | connecting | sending | reconnecting | stopping | error`. `DestinationVisibility = unknown | creatorReportedLive | providerConfirmedLive | providerReportedNotLive | providerError`. The top-level status shows OFFLINE, PREVIEWING, CONNECTING, SENDING, RECONNECTING or ERROR; after explicit Live Control Room confirmation it shows **LIVE — creator confirmed**, and with a future read-only provider signal it may show **LIVE — provider verified**. The qualifier is always visible. With manual URL/key, status remains SENDING and destination unverified until the creator confirms what they see in Live Control Room. An open socket alone never produces a LIVE label. On transport loss, both forms of LIVE revert immediately to RECONNECTING and the prior destination confirmation becomes stale.

| Local state | Entry evidence | Visible action | Destination visibility |
|---|---|---|---|
| OFFLINE | No active PCM/encoder/publisher | Open or restore program | Unknown; show last session outcome separately |
| PREVIEWING | Local clock, audio and frames advancing | Edit, audition, preflight | Not applicable |
| PREFLIGHTING | Checks running against a pinned program revision | Resolve blockers or cancel | Unknown |
| CONNECTING | Codec packets ready; RTMPS handshake/publish pending | Cancel connection | Unknown |
| SENDING | Publisher accepts timestamped packets | Stop; inspect Live Control Room; confirm viewer-live state | Unverified; after confirmation, top-level label becomes LIVE with creator/provider qualifier |
| RECONNECTING | Previously sending, now transport lost | Retry now, stop, monitor attempts | Prior confirmation becomes stale immediately |
| STOPPING | Drain/close requested | Wait; force stop only after timeout | Stale until provider says stopped |
| ERROR | Pipeline cannot continue safely | Fix cause, retry preflight, restore preview | Error/unknown; never a retained green LIVE badge |

A network loss keeps local playback/rendering active for a bounded grace period and reconnects with backoff; the UI says what viewers may be missing. A fatal audio-source loss changes the program to a safe holding scene/silent audio only if the creator opted into that recovery policy; otherwise end transmission visibly. A stream ending unexpectedly creates a persistent event and offers a verified retry path. Error cards say what failed, what remains saved, and the next action. Example: “Connection lost. Playback and visuals are continuing locally. Reconnecting; viewers may see an interruption.” The persistent program state records the error even if a toast was missed.

Preflight checks playlist eligibility, source availability, rights declarations, actual decoded-audio test, analysis coverage, metadata fields, title safe area, safety mode, encoder capability, resolution/fps/bitrate, destination format, key presence, network reachability/upload headroom, power/thermal state, free space for logs/recording, and mobile lifecycle constraints. “Go Live” remains a deliberate final action after the results. It does not silently create or publish a YouTube event.

Preflight presents blocking issues (no eligible audio, no key, encoder cannot start), actionable warnings (low upload headroom, missing analysis, potential Content ID issue), and information (mobile foreground condition, destination visibility unverified). A failed check never discards a playlist. Rerun one check when its input changes and retain the others until stale. Go Live is enabled only when blocking items are resolved. While live, health prioritizes current/next track, elapsed time, audio presence, connection, bitrate and dropped frames, with deeper metrics in an inspector.

### Four complete creator journeys

1. **First run:** The creator imports two eligible files. The app checks format and availability in the background, shows each track immediately, and asks for broadcast-rights status only when live use is requested. “Generate Visual Identity” begins track/program analysis, renders a provisional score quickly, then enriches future cues as analysis finishes. The creator auditions a track and metadata card, adjusts one guided control, and saves the playlist and preset automatically. Closing during analysis leaves a resumable job; relaunch opens the same playlist with its accepted visual identity.
2. **Go Live:** The creator selects a saved destination, sees the specific playlist and output profile, reviews preflight, and taps Go Live. The app first starts a local program and verifies encoded audio/video, then establishes RTMPS. It shows “Sending to YouTube; live status unverified” and a clear action to inspect Live Control Room. After the creator confirms the event is viewer-live there, the app shows “LIVE — creator confirmed.” It never silently changes YouTube event privacy or starts an API-managed broadcast. If the key is rejected, the message identifies the destination problem; the playlist and visual preset remain ready for retry.
3. **Network failure:** A brief disconnect moves local pipeline state to RECONNECTING, shows elapsed outage and attempt count, and keeps local audio/visuals running. After bounded retry, a fresh publisher connection sends codec configuration and a keyframe, then resumes SENDING. If the destination did not retain the event, the UI remains unverified and points to Live Control Room. If retries exhaust, it offers Retry Connection or Stop Program; no stale media backlog is replayed.
4. **Quit, crash, or relaunch:** A normal Stop confirms publication has ended and saves a resumable local session. An app/process failure is recorded as interrupted on next launch. The app restores playlist, source statuses, accepted preset, analysis, checkpoint and approximate playhead; it offers Preview from here and Run Preflight again. It does not auto-connect to YouTube or pretend a viewer stream continued while the process was absent. A missing source produces Locate File or Skip Track; the recovered playlist entry stays intact.

For a rights-declared track that vanishes mid-program, retain its declaration and analysis history but mark its asset `missing`; rights-valid never means file-available. If the next track is missing, the chosen live policy either skips to the next prepared, eligible item with an intentionally scored bridge, or shows a holding slate with silent audio for a configured bounded interval before ending. If the current file fails during decode, fade/stop at the next safe audio boundary and apply the same policy. Do not replay protected subscription audio, substitute a different recording by title, or silently loop the previous track. Error copy: “Track file is unavailable. Your playlist and rights note are saved. Locate the file or skip this track.”

## 4. System boundaries and ownership

One native process can own the initial broadcast. Keep modules as explicit Swift packages/targets where testing and realtime ownership benefit; avoid distributing a single-device MVP across a cloud backend. A future remote control service is optional and has no role in core playback or rendering. The UI sends commands; it does not own timing or hold raw PCM/frame histories.

```text
Local file access → decode/cache → program PCM mixer → audio output + analysis + AAC encoder
                                               │                 │
                                               └→ transport clock → Visual Score/Director → glyph scene state
                                                                           ↓
                                                                   Metal composition + safety
                                                                           ↓
                                                               preview lease + H.264 encoder
AAC and H.264 packets → timestamp interleaver/mux → RTMPS publisher → YouTube ingest
                          ↘ optional bounded local recording
Persistence: playlists, source refs, analyses, DNA, scores, presets, session checkpoints, destination config
```

`MediaLibrary` owns imported file references and source capabilities. `ProgramEditor` owns ordered track instances. `AnalysisService` reads permitted files off the audio callback, stores versioned features, and produces confidence/coverage. `ArtDirector` compiles playlist analysis plus locks/preset into Visual DNA and a score. `Transport` owns playback, seek/skip/crossfade, sample clock, and the single mixed PCM stream. `VisualEngine` owns scene state and frame production. `ProgramRenderer` applies titles/color/safety and yields frame leases. `Encoder` owns video/audio codec sessions and packet timestamps. `Publisher` owns RTMPS/TLS session, muxing, send queue, reconnect, and server feedback. `SessionStore` atomically persists edits/checkpoints. `HealthMonitor` collects bounded local metrics. `BroadcastCoordinator` is the only authority that applies state transitions and starts/stops the end-to-end pipeline.

Control calls are serialized through `BroadcastCoordinator` (an actor or equivalent isolated queue): `import`, `prepare`, `preview`, `seek`, `skip`, `acceptDraft`, `preflight`, `startSending`, `stopSending`, `recover`. Each command includes an expected session/revision where relevant and returns an accepted revision or typed failure. The audio callback and Metal submission are real-time lanes with preallocated, bounded buffers; actors never run in those callbacks. Analysis and score compilation run on cancellable worker tasks. Configuration changes cross to media lanes as immutable snapshots at scheduled boundaries. A stale analysis result cannot overwrite a newer playlist revision.

The visual contracts from Phase 1 §31.2 remain normative: `AudioAccessDescriptor`, `TransportSnapshot`, `FeatureFrame`, `MusicalEvent`, `TrackAnalysis`, `ProgramAnalysis`, `VisualDNA`, `VisualScore`, `SceneManifest`, `RenderSnapshot`, `FrameLease`, `EngineHealth`, `VisualCheckpoint`. Add `SourceRightsRecord`, `SourceAsset`, `TrackInstance`, `OutputProfile`, `Destination`, `BroadcastSession`, `PreflightReport`, `PublisherHealth`, and `RecoveryJournal`. All IDs are stable, all media times rational/sample based, optional values represent unknown explicitly, and every derived asset records source fingerprint plus algorithm version.

## 5. Persistent data model and consistency

Use an on-device database suitable for transactions and migration (SQLite through a thin repository layer is the initial choice) plus files for larger analyses/preview caches. Store secrets in Keychain, never in exported presets or diagnostic archives. Keep music files in place by default to avoid duplicating large libraries; optional managed copy is explicit. Bookmark blobs and file URLs are private local state, excluded from preset exports. Cloud sync is deferred; exporting a playlist manifest cannot export audio or rights claims as portable entitlements.

| Entity | Identity and essential fields | Lifecycle/invariant |
|---|---|---|
| `SourceAsset` | ID, source kind, bookmark/managed-relative path, fingerprint (size/modification plus content hash as available), codec/duration/channels, artwork provenance, availability | Revalidate before decode/live; missing file retains entry |
| `SourceRightsRecord` | Asset ID, creator declaration for sound/composition/artwork, scope/destination/territory if known, evidence note/reference, review date, status | Unknown by default; versioned changes; no app assertion of clearance |
| `Playlist` / `TrackInstance` | Playlist ID/revision; ordered instance IDs, asset ID, trims, gain, transition preference, metadata override | Duplicate tracks remain distinct instances; edits are transactional and invalidate only affected future score |
| `AnalysisJob` / `TrackAnalysis` / `ProgramAnalysis` | Source fingerprint, extractor versions, coverage, features/sections/confidence, progress/status/error | Resumable/cancellable; stale when source or estimator changes; partial remains usable with labels |
| `VisualDNA` / `VisualScore` / `Preset` | Versioned compiler/seed/resources, locks, scene assignments/cues, draft/accepted revisions | Existing DNA retained after playlist edits; presets have schema migration and missing-resource fallback |
| `Destination` / `OutputProfile` | RTMPS host/path and key reference; resolution/fps/color/bitrate/audio settings | Keychain reference only; validated host and no key in logs; profile capability-tested |
| `BroadcastSession` / `RecoveryJournal` | Session/epoch, transport state, current instance/sample, accepted score revision, cue cursor, last checkpoint, publisher attempt and error | Commit durable transitions; recovery never silently republishes after process restart without creator intent |

Relational keys: `TrackInstance.playlistID → Playlist.id`, `TrackInstance.assetID → SourceAsset.id`, `SourceRightsRecord.assetID → SourceAsset.id`, `TrackAnalysis.assetFingerprint → SourceAsset.fingerprint`, `ProgramAnalysis.playlistRevision → Playlist.revision`, `VisualScore.dnaRevision → VisualDNA.revision`, and `BroadcastSession.acceptedScoreRevision → VisualScore.revision`. A playlist edit increments its revision in the same transaction as ordered-instance changes. Analysis cache keys include source content fingerprint, trim/gain inputs where relevant, extractor version and channel/rate normalization version. A file edit invalidates dependent track analysis, then affected program analysis and future score cues; it does not delete the preset or hand-edited DNA. Artwork has its own provenance/rights status and may be omitted from output without invalidating audio analysis.

Persist the playlist and preset at each accepted edit; debounce only expensive serialized snapshots, then write atomically. Save a visual checkpoint at scene boundaries and a bounded interval, plus track boundary/transport discontinuity. If interrupted, reopen with the restored playlist, identity, playhead, and a choice to resume local preview. A live session is marked “interrupted”; credentials may remain in Keychain but the app does not go live on relaunch without a deliberate action. Long analyses use durable job records and resume from complete chunks. If source file changes, invalidate analyses by fingerprint and explain the reanalysis.

On iCloud Drive/Files imports, distinguish a coordinated, materialized local working copy from an external document reference. A file visible in a provider UI may still need download and may disappear during a network outage. The source lifecycle is `referenced → resolving → materializing/validating → ready | unavailable | changed`; each track shows its own state. The default on macOS is a durable security-scoped bookmark to a local file plus a short predecoded buffer. Files/iCloud providers on mobile require a stable local working copy before live use, subject to a visible size estimate and available storage. The creator can explicitly request a managed copy on macOS for unattended sessions. Copy atomically to an app-owned temporary path, validate format/fingerprint, then rename to a ready path; cancelled/failed copies are removed. Cache eviction is bounded by a configurable storage budget and cannot remove assets pinned by the active program. Revalidate before Go Live and when a track is queued. A working copy is not a grant of transmission rights. File coordination, bookmark lifetime, revocation and cleanup are device-test requirements. Source hashes are computed incrementally; no full audio file is loaded into memory solely to validate identity.

## 6. Playback, analysis, and time

For local files, use AVFoundation/Core Audio decode facilities, and own the **single program PCM bus** before it branches to speakers, feature extraction, and AAC. This avoids analyzing a different signal from the one transmitted. Prototype AVAudioEngine player/mixer/tap against interruption, overlap, and actual sample timing; if a tap cannot supply predictable program samples under all target paths, move to a more directly controlled render graph. Never do file I/O, allocation, database writes, or blocking locks in an audio render callback. [Apple AVAudioEngine](https://developer.apple.com/documentation/avfaudio/avaudioengine).

The program sample clock is authoritative. Each audio buffer has epoch, first sample position, sample count and presentation time. Video cadence derives from that media clock; the UI clock never drives the stream. Seek/skip/pause/restart create typed discontinuities and a new epoch where needed. Preanalysis can look ahead; online features declare window center and latency. The video renderer consumes a timestamped immutable feature snapshot and the committed score, never raw mutable callback state. Playback pause in preview freezes score time; a live pause policy is explicit (hold frame plus silent audio or end stream), with preflight wording.

Negotiate **three rates explicitly**: source decode rate per file; canonical program PCM rate after conversion/mixing; and analysis/AAC output rates. Phase 1 proposes 48 kHz analysis windows while YouTube currently recommends 44.1 kHz for stereo AAC. A candidate is 48 kHz floating-point program PCM, 48 kHz analysis, and a separately resampled 44.1 kHz AAC feed; choose this only after codec/device tests. Every resampler records input/output sample mapping and filter delay, so encoded audio PTS and feature timestamps map to the same program time. Route/device latency affects local monitoring and is measured separately from program timestamps. [YouTube encoder settings](https://support.google.com/youtube/answer/2853702).

Example: a 44.1 kHz source and 48 kHz source are each decoded and converted to the 48 kHz program bus. A two-second crossfade mixes both there. At program sample 480,000, the visual score observes exactly 10 seconds of program time; the AAC resampler has emitted approximately 441,000 output samples plus accounted filter delay. Audio encoder timestamps are mapped from program sample position, not inferred from wall-clock callback arrival. Video frame PTS at 30 fps uses the same rational timebase. Drift control compares submitted and accepted A/V timestamps and adjusts scheduling/drop policy within measured bounds; it does not stretch program audio to hide a stalled renderer. An A/V sync fault has a visible health code and a reproducible epoch/PTS trace.

Track boundaries support gapless transitions when files permit, optional scheduled crossfades on the program mixer, and visual bridges based on actual outgoing/incoming gain envelopes. Any overlap requires both assets to be broadcast-eligible; loudness handling uses measured gain and conservative clipping protection without changing the user's mix invisibly. Future tracks predecode a bounded buffer. A failed next track is skipped only according to user-selected policy, logged, and announced in creator controls. Local audio output can be muted without muting the encoded program; the UI makes those gains distinct. Device changes and mobile audio interruptions trigger clock discontinuities and an explicit recovery rule.

Feature analysis uses Phase 1's deterministic fast/phrase/track/program lanes; no ML is needed for RMS, spectral, onset or recurrence fundamentals. Full-track preanalysis is asynchronous and streaming, with bounded storage. “Verse/chorus/drop,” genre, valence, vocals and instruments remain uncertain advisory labels with provenance. Structure A/B/A′ and measured boundaries drive direction even without semantics. Rendering is autonomous when audio analysis is unavailable, but the creator is told that music response is limited. The initial launch's eligible local files should normally provide full PCM and analysis.

## 7. Visual engine integration and rendering

The art director compiles playlist summaries and a preset into a revisioned Visual DNA and bounded Visual Score. It respects user locks, resource caps, safety profile, scene cooldowns, reading windows and a commit horizon. Three deep episodes—Phase 1's city/engine/negative-space candidates—must prove causal visual action before the library grows. A `SceneManifest` declares typed controls, dramatic actions, persistent entity carriers, quality variants, title anchors, resource budget and checkpoint schema. Changes to a live draft are compiled off the render thread; `BroadcastCoordinator` swaps an immutable accepted snapshot at a safe boundary. Invalid edits never destabilize the live program.

Render order: select time-aligned score/feature snapshot → update bounded scene state → construct glyph/material geometry → rasterize glyph atlas/geometry in Metal → composite background, structures, reactive objects, atmosphere, typography, effects and broadcast graphics → map semantic palette and Rec.709 output → apply mandatory post-composition photosensitivity/motion checks → hand off a `FrameLease` to preview/encoder. Strict ASCII is a selectable art profile; Unicode box/Braille/block characters are an opt-in expanded profile with tested font shaping and safe fallback. Metadata uses native script shaping even when the artwork profile is strict ASCII. A shader-to-characters conversion can be one material, never the entire scene language.

Now-playing title/artist appear at approximately the first and final ten seconds, adjustable by the user. Short tracks and unknown duration use a protected, non-overlapping policy. Readability wins over an environmental title trick; the renderer can reserve a quiet title layer. On-screen elapsed/remaining and artwork are opt-in and rights-aware. Section transitions preserve subject continuity; track transitions choose compatible bridges, carry an entity when feasible, and avoid immediate repeats. Score seeds, stream names, compiler versions and checkpoint state allow a scene to reconstruct after seek and aid reproducible failure reports. Across playlist loops, the cycle seed advances and motif history is bounded, so the show evolves without resetting to frame one.

The safety envelope is enforced on fully composed, color-converted **candidate raster frames before encoder submission or publication**, after effects and title composition. A rejected candidate frame is replaced or held before it can reach the encoder; asynchronously examining already encoded frames would be too late. Photosensitivity Safe restricts available effects and luminance-change rate, including transitions and adaptive quality changes. Reduce Motion substitutes held shots and local detail changes for camera travel/shake. Encoded output is also audited in tests to catch color/codec effects. Do not claim clinical safety until the test protocol in Phase 1 §29 passes; offer the safer mode as an engineering control, not a medical guarantee.

Quality scaling removes distant detail, secondary atmospherics, costly feedback passes and optional 4K work before harming titles, focal action or audio timing. Bounded frame pools and queues prevent slow preview/encoder consumers from accumulating frames. Preview may drop old frames; encoder receives monotonic PTS and an explicit policy for late frames. Every frame lease has readiness, ownership, color metadata, dimensions and release obligation. Start with SDR Rec.709 8-bit; 1440p and 4K are measured later, not assumed from hardware marketing.

## 8. Encoding, muxing, and YouTube transport

The interoperability baseline is H.264 video, AAC stereo audio, RTMPS, 2-second keyframes, constant target bitrate, square pixels, progressive scan, and Rec.709 SDR 8-bit. YouTube's current encoder guidance recommends 44.1 kHz stereo/128 kbps AAC and lists 720p30 ≈4 Mbps, 1080p30 ≈10 Mbps, 1440p30 ≈15 Mbps for H.264; actual profiles depend on uplink and device qualification. Its two official pages differ on newer codecs over RTMPS, so HEVC/AV1 must pass an ingest experiment before being offered. [YouTube encoder settings](https://support.google.com/youtube/answer/2853702), [ingestion protocol comparison](https://developers.google.com/youtube/v3/live/guides/ingestion-protocol-comparison).

Use VideoToolbox's real-time compression path for video and an evaluated AVAudioConverter/AAC path for audio; a transport library may instead own codec sessions, but **exactly one component owns each encoder**. Prototype [HaishinKit.swift](https://github.com/HaishinKit/HaishinKit.swift) only if it accepts externally rendered Metal/CVPixelBuffer frames and program PCM/AAC with correct timestamps, reliable RTMPS/TLS, bounded queues, and reconnection; its repository claims iOS/macOS support, which is a candidate, not verified product behavior. Apple documents `VTCompressionSession` for live encoding. [Apple live video encoding](https://developer.apple.com/documentation/videotoolbox/encoding-video-for-live-streaming), [AVAudioConverter](https://developer.apple.com/documentation/avfaudio/avaudioconverter).

The mux/publisher interleaves encoded packets by PTS/DTS, writes codec configuration before media, retains monotonic timestamps within a publishing epoch, and explicitly handles reconnect discontinuity. The RTMPS URL is parsed/validated; the stream key is Keychain-held and redacted. TLS validates hostname and uses SNI; YouTube describes RTMPS on port 443. Do not log full URLs when they contain keys. [YouTube RTMPS guide](https://developers.google.com/youtube/v3/live/guides/rtmps-ingestion).

Backpressure policy: bounded encoded packet queue; never let network delay block the audio callback. Local audio continues through a network outage; the publisher drops packets that have become too old for a live stream, including stale audio, rather than replaying a delayed backlog. If the buffer budget expires, disconnect and reconnect with fresh codec configuration and a keyframe. Reconnect uses capped exponential backoff with jitter, network-path awareness and a maximum attempt window set by the user. On return, request an IDR and rebase/reinitialize ingest timestamps as required by the chosen transport. Local preview/playback continue during reconnect unless a user policy says otherwise. A prolonged failure moves to `ERROR` with the playlist and visual state preserved; it cannot silently terminate. Local recording may keep a separate file with its own finalization and free-space guard; its success does not prove YouTube viewer-live status.

Manual URL/key is the MVP configuration. An optional later YouTube integration would use OAuth with narrow scopes, create/list `liveBroadcast` and `liveStream`, bind them, observe stream health and transition event status deliberately; these are distinct resources and actions. No OAuth is required for an offline preview. [YouTube Live API workflow](https://developers.google.com/youtube/v3/live/guides/implementation/broadcasts-and-streams), [broadcasts and streams](https://developers.google.com/youtube/v3/live/broadcasts-and-streams).

In manual-key mode, Stop confirms that **local sending stopped** and the RTMPS session closed. It cannot assert that the YouTube event has ended; depending on the event's auto-stop setting, the creator may need to end it in Live Control Room. The Stop result presents that action and leaves destination visibility unverified/stale until checked.

## 9. Reliability, security, and observability

The app records bounded local diagnostics: media clock drift; audio underruns/clipping; feature age/coverage; frame render percentiles/drops; encoder latency, keyframe interval and output bitrate; queue occupancy; reconnect attempts; ingest errors; thermal/energy state; source access failures; safety suppression; checkpoint age; and accepted DNA/score revision. Logs never include raw keys, file contents, full user paths unless explicitly exported, or unneeded personal metadata. A diagnostic export requires a user action and redacts secrets. Health status maps to plain language first, details second.

Failure policies are explicit: unavailable next asset → repair/skip/stop according to preset; analysis failure → autonomous performance with status; renderer overrun → step down quality and hold a valid frame; encoder failure → stop publishing and offer restart after rebuilding codec state; network loss → reconnect while local program continues; access revocation → preserve playlist and offer reselect; app crash → restore offline and show interrupted broadcast; corrupt preset → last-known-good version plus report. Each transition is journaled once with an idempotent event ID. Alerts are rate limited so a multi-hour channel remains usable.

No server stores audio, stream keys, or playlists in the first release. App sandbox and platform file access apply. Destination input rejects unsupported schemes, malformed hosts, and accidental pasted keys in non-secret fields. Keychain access is scoped to the local app. Third-party libraries undergo license and maintenance review. Telemetry is opt-in or strictly local by default. Platform and provider terms, app review rules, and music rights are launch gates, not assumptions.

## 11. Verification strategy and objective criteria

Unit/property tests cover schema migrations, capability gates, source-rights states, score invalidation, deterministic seeds, cue idempotence, timing math, bounded queues, and safety rule enforcement. Integration tests use eligible local fixtures for decode → analysis → program PCM → AAC, score → glyph scene → final frame, and encoded A/V timestamps → local recording/RTMPS test receiver. Fixtures include silence, odd meter, tempo ambiguity, a short track, a long file, Unicode titles, corrupted audio, missing artwork and mixed sample rates. Golden images validate typography and glyph rendering across resolution, font and accessibility profiles without freezing the whole generative work to one screenshot.

Device tests measure sustained 720p/1080p profiles, thermal/power behavior, scene render percentiles, A/V offset and drift, missed keyframes, reconnect time, memory/pool growth, app lifecycle and audio interruptions on representative supported hardware. Mobile tests explicitly cover screen lock, app backgrounding, phone call/route changes, low power, Stage Manager, and network switch; supported behavior is documented from results. Mac tests cover sleep prevention policy, display disconnect, power/network changes and process restart. A synthetic receiver cannot replace a private/unlisted YouTube ingest trial. Confirm viewer-visible state in Live Control Room and playback after encoder connection, and test copyright interruption UX with authorized content when feasible.

Accessibility checks include VoiceOver/keyboard end-to-end flow, Dynamic Type layout, localization expansion, title legibility on encoded frames, color-blind modes, Reduce Motion, Increase Contrast, and photosensitivity tests on the **final encoded frames** including cuts and adaptive-quality transitions. A human review checks whether controls feel like a creative instrument rather than a diagnostic panel.

Product proof follows Phase 1 §30: blind comparisons against simple equalizer/reactive texture and a looped scene; observers should perceive identity, meaningful musical structure, continuity between songs, readable titles, and variation over hours. Test quiet and high-energy programs, unfamiliar genres, and low-confidence analysis. The release cannot claim that a channel is compelling merely because frames are unique or beat aligned. Track unknown/partial analysis as honest coverage, not a passing score.

Proposed controlled-release gates, to be revised only after measured prototypes: (a) 100% of live queue items pass technical/source/rights checks at preflight, with explicit revalidation before play; (b) 8-hour supported macOS run with no renderer crash, no unbounded queues, and Phase 1's <5% comparable-workload memory change after warmup; (c) Phase 1 high-confidence cue p95 error ≤50 ms, renderer-caused frame deadline misses <0.1%, no burst of more than three in healthy supported conditions; (d) measured audiovisual offset within ±100 ms at ingest/recorded playback over a representative hour, with no accumulating drift; (e) no false provider-confirmed LIVE badge in manual-key mode, and every induced network outage produces a visible RECONNECTING/ERROR state within the next health update; (f) every induced app restart restores playlist, accepted preset, source statuses and a usable preview without automatic publication; (g) 100% of release-corpus frames pass the chosen safety procedure before encoding, including transitions and title changes. The precise device matrix, reconnect window and upload-headroom threshold are selected after prototype data. Phase 1's comparative preference, identity, readability and repetition gates remain required for the claim that the visual broadcast is worth leaving on screen.

## 12. Open decisions for implementation spikes

1. Choose minimum OS/hardware after measuring Metal/VideoToolbox sustained load and mobile foreground behavior. Do not invent a compatibility guarantee now.
2. Confirm whether AVAudioEngine graph/tap gives the exact mixed PCM and timestamps needed through crossfade, local monitoring and route changes; adopt a directly controlled render path if it does not.
3. Prove one encoded frame path from Metal output to VideoToolbox to RTMPS with correct color tags and PTS, including title and safety checks.
4. Evaluate transport library versus a narrow owned publisher using custom-frame ingestion, key handling, reconnect and license criteria. Avoid two codec owners.
5. Measure latency budget and A/V drift on actual devices and YouTube ingest; choose alignment delay from evidence.
6. Set profile thresholds, reconnect limits and duration targets only after sustained device/network tests.
7. Recheck Apple, Spotify and YouTube terms before any future source integration; a new API capability alone does not resolve synchronization or public transmission rights.

**Build contract:** the first release is an offline-first native studio that can produce a music-aware, safe, coherent preview from eligible local audio, then deliberately publish that exact program to YouTube RTMPS with observable health and recoverable state. A successful demo must show a playlist-level identity evolving across tracks, source/rights gates that tell the truth, an encoded frame/audio path with measured timing, and failure behavior that preserves the creator's work.
